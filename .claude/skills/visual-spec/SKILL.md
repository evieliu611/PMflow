# /visual-spec — 圖文對照需求文件包

把定稿的雛型 ＋ 規格，整理成**技術團隊拿來開發、驗收的一組文件**，規則固定，之後換功能、換版本都能快速重產。

## 文件包組成（同一個功能、同一個版本 v{n}）

| 產物 | 位置 | 來源 | 誰產 |
|---|---|---|---|
| 需求規格 | `03_規格文件/01_需求規格_{功能}_v{n}.md` | 雛型 SPEC ＋ 確認紀錄 | **/spec-gen**（本 skill 不重寫，缺了就先請 PM 跑它） |
| 圖文對照需求說明 | `03_規格文件/{功能}_需求說明_圖文對照版_v{n}.html` | `_圖文對照_content.js`（人工／AI 維護）＋ 畫面截圖 | `assets/build.js` |
| 驗收條件文件 | `03_規格文件/{功能}_驗收條件_v{n}.html` | 規格 md §六 AC 表（自動抽取） | `assets/build_ac.js` |
| 雛型規格檢視頁 | `02_雛型/雛型_v{n}_*.html` 的 `?spec=1` | 規格 md（自動轉 HTML 灌入） | `assets/inject_spec.js` |

三份文件的**連結按鈕**（圖文對照標題列）固定順序：`▶ 開啟雛型` → 其他附件（如 Excel 範本）→ `📄 需求規格文件` → `✅ 驗收條件文件`（**驗收條件放最後一個**）。圖文對照每一節另有「開啟雛型：{畫面}」按鈕，直接用 `?state=` 開到該畫面。**不放**「雛型規格檢視」連結（規格檢視頁就是規格文件本身，不必另給）。驗收條件文件的標題列回連圖文對照、規格文件、雛型。

## Usage

```
/visual-spec 專案/{專案名}/功能/{功能名}            # 完整產出／同步三份文件
/visual-spec ... --只出 圖文對照                    # 只重產圖文對照
/visual-spec ... --只出 驗收條件                    # 只重產驗收條件文件
```

前置：功能資料夾已有最新版雛型 `02_雛型/雛型_v{n}_*.html`、畫面截圖 `02_雛型/畫面截圖/`、規格 `03_規格文件/01_需求規格_*_v{n}.md`。缺規格 → 提醒 PM 先跑 `/spec-gen`；缺截圖 → 先依 spec-gen 步驟 7 截圖。

## 步驟

1. **盤點**：讀功能資料夾的 `README`／需求摘要／最新版雛型（取檔名版本號最大者）／規格 md／專案 `memory/`。三者版本號必須一致，不一致先回報 PM。
2. **內容設定檔**：
   - 首次：複製 `assets/content.template.js` 到 `03_規格文件/_圖文對照_content.js`，依雛型逐畫面填 `sections`（每畫面一節：標題、F-編號、開啟雛型按鈕、截圖＋圖號熱點、右側說明列）。可參考完整實例 `references/競合分析_content_範例.js`。
   - 更新：已有設定檔 → 只改異動處，**保留既有內容**（不要整份重生）。
   - 內容來源是**規格 md 與雛型 SPEC**，不要另外發明；待定處標 `Q`（見下方規則）。
3. **圖號位置**：圖上編號 `hs:[編號,x,y]` 的 x、y 是**截圖像素座標**。截圖或版面一變就要重新量；用 Read 看截圖估座標，**不要沿用舊座標**。圖號＝右側說明列序號（build 會警告超出列數的圖號）。
4. **產出**（在 skill 的 `assets/` 下，`--root` 指到功能資料夾；Windows 路徑含中文請加引號）：
   ```bash
   node .claude/skills/visual-spec/assets/build_ac.js     --root "<功能資料夾>"
   node .claude/skills/visual-spec/assets/inject_spec.js  --root "<功能資料夾>"
   node .claude/skills/visual-spec/assets/build.js "<功能資料夾>/03_規格文件/_圖文對照_content.js" --root "<功能資料夾>"
   ```
   `build_ac.js` 與 `inject_spec.js` 會自己找最新版雛型與規格 md、功能名與版本號；圖文對照的輸出檔名由設定檔 `out` 決定（版本號請跟雛型一致）。
5. **驗證**：用瀏覽器（或 headless Chrome，完整絕對路徑／`file:///` URL）開圖文對照看：圖號有沒有落在對應位置、點圖號是否只顯示該項、漢堡大綱可開、按鈕連結可點。驗收條件文件看測項數與規格 §六 是否相同。
6. **收尾回報**：列出三份文件路徑、AC 條數、尚未核對的圖號位置、規格中仍待確認的項目。不確定的地方如實說，不要說「已驗證」。

## 圖文對照版寫作規則（讀者是技術團隊，來自實際使用的決定）

- **只寫「現在要做什麼」**：不寫「已確認」「PM 確認日期」「原本是…改成…」之類的決策歷程；也不放「決策歷程」章節。
- **只標待確認**：待確認用 `❓ 待確認` 標籤並集中列在文件開頭「待確認事項」表（含決策者：技術／客戶／PM）；**暫定項目先依雛型實作**，客戶有意見再調。沒有待確認就不放該表。
- **圖號互動**：左側畫面、右側規格；點圖上圖號只顯示該項說明，再點還原；右側列的圓形序號同理。每節都有「顯示全部」。
- **導覽**：標題旁漢堡按鈕收合大綱（目前所在章節即時顯示），側欄為快速跳轉；總覽章節含「背景與目標」（最上）→ 系統架構圖（可選）→ 畫面總覽縮圖（點了跳到該節）→ F-編號功能表 → 其他總覽卡片。
- **選項直接列出**：欄位表的選項值（縣市、類型、狀態…）全部列出，不要寫「見雛型」。
- **用語**：繁體中文（台灣用語）；縣市用「臺」（臺北市…）、「台糖」維持「台」；用「坐標」不用「座標」。
- **圖示對照章（選用）**：專案規定了圖示庫時，設定檔填 `icons` 與 `iconNote`，文件會產出第 4 章列出名稱與連結；不需要就留空陣列，該章與側欄連結都會省略。
- 其餘約束（雛型風格、版本規則、鐵律）一律依專案 CLAUDE.md；**單一真實來源是雛型**，文件是從雛型彙整，改版從雛型改起。

## 專案專屬規則（依專案決定，不是固定規則）

以下是韋能案的決定，其他專案開跑前要先問 PM 是否適用，不要直接沿用：

- **資訊視窗以現有系統公版為準**：現有系統已有公版的畫面，不過度規定細節，註明「以公版為準」。
- **圖示一律用 Material Icons（Outlined）svg，不用 emoji**，圖示對照章列名稱與 Google Fonts 連結。

- **狀態符號用黑色文字 `v`／`-`、不用 emoji**：這只是競合分析「資訊視窗開發階段」這個功能的需求，其他功能不一定適用。

新專案或新功能如有類似的規則，記在該專案 `memory/`，並寫進該功能的 `_圖文對照_content.js` 註解。

## 驗收條件文件規則

- AC 內容**只從規格 md §六 抽取**（表頭：AC｜類別｜對應 F｜Given｜When｜Then｜PG自測｜PM驗收｜備註）；要改測項就改規格，再重跑，不要直接改 HTML。
- 功能：類別／F-編號篩選、關鍵字搜尋、「只看未完成」、勾選結果存在瀏覽器 localStorage（key 含功能名與版本）、匯出 CSV、清除勾選。
- 流程文字固定：PG 交付前全勾「PG自測」才交 PM；PM 勾「PM驗收」；不通過在備註寫現象：bug → PG 修復後複測；需求認知差異或客戶改需求 → 回 `/req-intake` 從雛型改起。
- 結果留存放 `05_驗收/`（匯出的 CSV 與不通過項目處理紀錄），不另產清單。

## 雛型規格檢視頁

`inject_spec.js` 把規格 md 轉成 HTML 灌進雛型 `#spec`（`?spec=1` 才顯示），並在 `_shared.css` 追加一次樣式。**前提**：雛型內已有 `document.getElementById('spec').innerHTML=` 這段與 `/* ===== 啟動` 註解當作定位記號；沒有就先在雛型補好再跑。這是「雛型規格檢視內容＝規格文件」的做法，不要在雛型裡另寫一份。

## 環境注意

- Node 即可執行，無額外套件。圖文對照把截圖以 base64 內嵌，檔案可達數 MB，屬正常。
- Bash 的 `python` 在此環境可能是 Windows 商店殼，需要 Python 時用 `py`；不要寫含中文的 `.ps1`。
- 截圖用 headless Chrome 時必須完整絕對路徑；帶 `?state=` 這類查詢字串要用 `file:///` URL 且中文路徑 URL-encode（見 spec-gen 步驟 7）。
- 此工作區沒有版本控制：重產會覆蓋同名 HTML，但設定檔與規格 md 是來源，可隨時重跑還原。
