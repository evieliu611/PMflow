# /flow-status — 流程狀態檢查（唯讀儀表板）

把「靠紀律維持的兩條鐵律」變成「靠檢查偵測」。這支 skill **只讀不寫**：掃描功能資料夾，回報目前階段、版本一致性、變更懸置項、全鏈一致性，並指出下一步。它不修改任何產物——發現問題時引導 PM 去跑對應的 skill（多半是 [change-impact]）。

為什麼需要它：CLAUDE.md 說「看到版本號對不上，代表有文件沒同步」，但先前沒有任何機制**主動偵測**這件事——一致性全靠人眼翻資料夾。這支把那份隱性成本收成一個指令。

## Usage

```
/flow-status 專案/{專案名}/功能/{功能名}      # 單一功能的完整狀態
/flow-status 專案/{專案名}                     # 掃全專案，每個功能一列摘要
/flow-status                                   # 掃 專案/ 下所有專案的功能總覽
```

- 唯讀：不建立、不修改、不刪除任何檔案，也不改 README／memory。
- 範圍越大摘要越粗：全專案／全域模式每功能只出一列（階段＋版本一致性＋懸置數），單功能模式才出完整報告。

## What You Must Do When Invoked

### 步驟 1：確定掃描範圍
- 給了 `功能/{功能名}` → 單一功能完整報告（步驟 2~6 全跑）。
- 只給到 `專案/{專案名}` → 列出該專案 `功能/` 下每個功能，各跑步驟 2~5 的精簡版，出一張總表（步驟 7）。
- 什麼都沒給 → 掃 `專案/` 下每個專案（跳過 `_範本專案`），出跨專案總覽。

先讀該專案的 `memory/MEMORY.md`（若有）掌握背景，不要重掃整棵樹。

### 步驟 2：判定目前階段（看哪些子資料夾有實質產物）
依子資料夾與檔案存在性判定走到哪，**空資料夾不算數**（範本 cp 過來會有空殼）：

| 階段 | 判定依據（該路徑下有非空產物） |
|------|--------------------------------|
| 0 需求整理 | `01_需求整理/01_需求摘要.md` |
| 1 雛型 | `02_雛型*/` 下有 `.html` |
| 1.5 回饋回填 | 存在 `02_雛型_v2/` 以上，或雛型內有 `訪談紀錄_*.md` |
| 2 規格 | `03_規格文件/01_需求規格_*.md` |
| 3 開發準備 | `03_規格文件/02_開發任務拆解*`、`03_API介面定義*`、`04_資料表設計*` |
| 4 驗收 | `05_驗收/驗收清單_*.md` |

「目前階段」取**最遠**有產物的階段。同時記錄**缺漏的中間階段**（例如有規格卻沒雛型 v2，代表訪談回饋可能沒回填就展開了——這是異常，要標紅）。

### 步驟 3：版本一致性檢查（鐵律的核心體檢）
從各產出檔名與抬頭抽版本號，攤成一張表比對：

- 雛型：取 `02_雛型/`、`02_雛型_v2/`… 中版本號**最大**者為當前版。
- 規格：`01_需求規格_*_v{n}.md` 的 n。
- 開發包三件、驗收清單：各自的 `_v{n}`。
- 也讀檔案抬頭的 `> 依據：..._v{n}` 行，比對「檔名版本」與「宣稱依據版本」是否一致。

判定規則：
- ✅ **一致**：當前雛型版 = 規格版 = 開發包版 = 驗收清單版。
- ⚠️ **落後**：某下游版本 < 雛型版（例：雛型已 v3，規格還 v2）→ 代表雛型改了下游沒跟，**列為待同步**，指向 change-impact。
- ⚠️ **來源不符**：檔名 v3 但抬頭「依據 v2」→ 產出當下就沒對齊，標可疑。
- 只走到某階段、下游還沒產出 → 不算不一致，標「未產出」即可。

### 步驟 4：變更懸置項掃描（影響矩陣沒勾完的變更）
掃 `06_變更紀錄/變更_*.md`，對每份：
1. 讀「三、影響矩陣」表格，數還是 ☐（未勾）的列。
2. 只要有任何 ☐，該變更就是**懸置中**——列出：變更摘要、日期、未完成的列（產出物＋負責角色），特別點出 `PM+AI` 負責卻沒勾的（那是 PM 自己該收尾的）。
3. 讀抬頭的「合約範圍」，若為 ⚠️／❌ 且沒有後續定案紀錄 → 提醒「這筆還卡在待商務確認，別忘了回覆客戶前先跟主管確認」。

沒有 `06_變更紀錄/` → 這節回報「無變更紀錄」，跳過。

### 步驟 5：全鏈一致性抽查（下游對不對得上上游）
這是 spec-gen 的一致性檢查**沒涵蓋到的後段**。只在單一功能模式做，且是**抽查非窮舉**（列疑點給人確認，不臆斷）：

- **規格 ↔ API**：規格欄位表／AC 提到的查詢條件、輸出欄位，API 定義的 Request/Response 是否有對應？API 有、規格沒有的欄位要標出。
- **規格 ↔ 資料表**：規格欄位表的資料來源欄位，資料表設計是否有對應欄（或標了 `【需 PG 確認】`）？
- **規格 AC ↔ 驗收清單**：每條 AC 是否都有至少一個驗收測項對應？漏掉的 AC 標出。
- **F-編號完整性**：追溯表（規格 §七）的 F-編號，是否都能在需求摘要找到源頭、在雛型 SPEC 找到落點？孤兒 F-編號（下游有、上游查無）標出。

發現不符**只回報、不修改**——這些多半要走 change-impact 或回頭補規格。抽查抓不準的一律標「疑」，交 PM 判斷。

### 步驟 6：輸出單一功能儀表板
在對話中直接輸出（不寫檔），格式：

```markdown
# 流程狀態：{功能名}
掃描時間：{今日}

## 目前階段
階段 {N}：{階段名}｜{一句話：正常推進 / 有異常}

## 版本一致性
| 產出 | 版本 | 依據抬頭 | 狀態 |
|------|------|----------|------|
| 雛型 | v3 | — | 當前 |
| 規格 | v2 | 依據 v2 | ⚠️ 落後雛型一版 |
| 開發包 | v2 | — | ⚠️ 落後 |
| 驗收清單 | — | — | 未產出 |

→ 判定：{一致 / 有 N 處待同步}

## 變更懸置項
- 變更_v3_案場可多選（2026-07-20）：影響矩陣還有 2 列未勾（API-PG、資料表-PG）
  合約範圍 ✅，PM+AI 的項目已完成

## 全鏈一致性抽查
- ⚠️ AC-05「匯出逾時提示」在驗收清單找不到對應測項
- 疑：API 的 `type` 參數在規格欄位表沒看到，請確認是否遺漏

## 下一步建議
1. 雛型 v3 → 規格還停在 v2：跑 /change-impact 把下游推上來（或確認 v3 只是小改不影響規格）
2. 變更_v3 的 PG 項目：把影響矩陣轉給 PG，完成後回來勾掉
3. 補 AC-05 的驗收測項
```

原則：**先講結論**（階段＋一致/不一致），再列細節，最後給可執行的下一步。沒問題的功能就明確說「一致、可往下走」，不要為了填版面硬找問題。

### 步驟 7：專案／全域模式的總表
多功能時每功能一列，不出完整報告：

```markdown
# 專案流程總覽：{專案名}
| 功能 | 階段 | 版本一致 | 變更懸置 | 需注意 |
|------|------|----------|----------|--------|
| 1.2.2 歷年清冊下載 | 4 驗收 | ✅ | 0 | — |
| 1.3.1 案場管理 | 2 規格 | ⚠️ 規格落後 | 1 | 跑 change-impact |

→ 共 N 個功能，X 個有待同步／懸置項。要看某功能細節：/flow-status 專案/{專案名}/功能/{功能名}
```

## 注意事項
- **唯讀是鐵則**：這支 skill 的價值就是「安全地體檢」。絕不代 PM 動手改版本、勾矩陣、改文件——那些是 change-impact / 各階段 skill 的職責，flow-status 只負責**發現與指路**。
- **不臆斷**：版本、對應關係判不準時標「疑」列出，交 PM 確認，不要當成事實回報。空資料夾、範本殘留不要誤判成「已完成該階段」。
- **抽查非窮舉**：全鏈一致性是抓明顯斷點，不是逐欄 diff；報告要讓 PM 知道「這是抽查結果，最終以人判斷為準」。
- 版本一致性與變更懸置的判定邏輯，正是 [spec-gen]、[dev-kit]、[accept-gen]、[change-impact] 各自零散重複的「版本比對／提醒」的集中版——它們仍各自把關，這支提供全域視角。
- 這支貫穿全程、隨時可跑，與 [change-impact] 是一對：change-impact 負責「改」，flow-status 負責「查改完了沒」。
