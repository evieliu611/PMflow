PMflow 流程優化討論

彙整這輪 PMflow 試用的痛點、五個議題的建議做法，以及今天需要一起拍板的決策。

SyncSpec PM 會議 2026 / 09 / 21 討論用 · 非定稿

今天要解的核心問題

試用有效，但暴露出七個議題。它們看似分開，其實是同一個結構性問題的不同症狀。

PMflow 試用的初衷

  • PM 規劃時就用 AI 來回討論可行性、產出 HTML 雛型
  • 先找 PL 確認方向，把待確認事項帶去客戶訪談
  • 確認完再產規格，PG 直接照規格開發
  • 目的：把翻案風險從最貴的階段往前移

試用後浮現的七個議題

  • ① 想提早到「投標／服務建議書」階段
  • ② 規格圖／Figma／HTML 對不上（可否 AI 產設計）
  • ③ 規格文件難讀（含「給人看 vs 給 AI 看」）
  • ④ 單機版：多 PM 成果分岔、難即時同步給 PL/PG
  • ⑤ 資料夾想改，並支援專案管理與自動產文件
  • ⑥ 明定流程時間點：文件該在何時給 PL 看
  • ⑦ 接上開發現實：讀既有 DB/API、補完整流程圖
今天的產出：七個議題各自的方向共識，以及最後一頁「需要拍板的決策」逐項圈選。

痛點盤點：表層要求 ≠ 背後真正的痛

把「大家講出來的建議」還原成「背後真正的痛」，才不會只解到表面。

#表層建議背後真正的痛現在卡在哪
1提早到投標階段技術團隊 太晚進場；啟動會議想像落差大投標粗雛型與 PMflow 雛型是兩份，要重畫重想像
2AI 產設計、規格圖要跟 Figma 一致規格圖／Figma／HTML 三份對不上、PG 混淆；設計還要重畫同一畫面多份來源；HTML⇄Figma 雙向是真難點
3規格難讀、AC 獨立、人/AI 分版規格是寫給人讀的，卻用「抽取邏輯」排版AC 才剛刻意併進規格 §六（為單一來源）
4放雲端/NAS 解多人協作多 PM 成果分道揚鑣、資訊難即時同步目前為單機作業、尚無版本控制
5調整資料夾、做專案管理共用檔重複跑浪費 token；未來想自動產文件資料夾按「產物」切，還沒有「專案管理層」
6明定流程時間點產了文件卻沒在對的時間點給 PL看＝沒用缺明確「PL 介入時機」；PL 常有多專案、有些還沒投入
7接上開發現實流程沒讀 DB/API、缺完整流程圖，雛型欄位與既有系統對不上PM 主線刻意不碰技術，但需求需錨定現實
共同的敵人只有一個：「文件／畫面／程式各自演化」。七個議題若用直覺做法，都會不小心生出「第二份會分岔的來源」或「產了卻沒接上的文件」。

一條貫穿五個議題的總方針

SINGLE SOURCE · MULTIPLE VIEWS

單一來源，多重視圖

來源只有一份，輸出可以有很多份，每一份對準一個對象或一個階段。

這不是新概念——你們的雛型已經在這樣做了：

雛型現況（已驗證的做法）

  • 同一份 HTML 雛型 = 唯一真實來源
  • ?notes=1 討論圖層 → 給客戶 / 主管看未決事項
  • ?spec=1 規格圖層 → 給 PL / PG 看規格

把同一招套到五個議題

  • 投標階段 → 雛型的「輕量視圖」，不是另一份檔
  • 給設計 / Figma → 雛型的「匯出視圖」，不回流改來源
  • 規格難讀 / AC 獨立 → 同一份規格，出多種閱讀版
守住「來源一份、視圖多份」，五個議題都能做，且都不破壞單一真實來源。

議題一：規格難讀 → 一源三視圖

同一份 SPEC 雛型，經 spec-gen 產出三種視圖，各對準一種對象。

來源：SPEC 雛型（唯一真實來源） ── spec-gen 抽取
▼
PM 確認 · 需求說明會議

① 人讀版

圖文左右對照，好掃、好懂、有畫面；用來確認「符不符合想像」。

PG 餵給 AI 開發

② AI 讀版

文字自我完備、不靠圖、帶穩定 ID、邊界全攤開；可附 SPEC 雛型 HTML。

PG 自測 · PM 驗收

③ 驗收清單版

AC 獨立成冊，開發時不必一起翻；含負向/權限測項與勾選欄。

關鍵：人讀版最強的「圖文對照」，正是 AI 版最弱的「意義藏在圖裡」。三版同一次產出、版本鎖死；AI 版是投影，絕不手改。最好做 建議當 SyncSpec 首勝。

議題二：提早到投標階段（投標視圖）

不是「另開一份投標雛型」，而是讓同一份雛型從投標一路長大到規劃。

現況：兩份、要重想像
  • 業務投標畫一份粗雛型（拋棄式）
  • 得標後 PM 重新畫 PMflow 雛型
  • 啟動會議大家從頭想像 → 落差
建議：一份、連續生長
  • 投標模式產「願景雛型」：低精度、可點擊、不掛厚 SPEC
  • 得標後同一份原地升版、往上疊 SPEC
  • 投標 → 啟動 → 規劃 看的是同一張畫面在長大
風險提醒：投標畫進去的東西容易被客戶當成已承諾功能。投標視圖要更嚴格標「示意 vs 承諾」，合約範圍判定（✅內⚠️模糊❌超出）要提前介入。

議題三：AI 產設計 + Figma（1/4）議題三的由來

PG 讀需求規格時，規格裡的圖 ↔ Figma ↔ HTML 三份對不上，不知以哪個為準。根因：同一個畫面有多份會分岔的來源。

現在的痛：一個畫面、三份來源

  • 規格文件的圖 = 另外截一張存進去
  • Figma = 設計師另畫一版
  • HTML 雛型 = 又一版
  • → 三份各自演化，PG 混淆、對不上

目標原則：一畫面一來源

  • 一個畫面，只有一個視覺來源
  • 規格的圖不自己存，而是「引用」單一來源自動產生
  • 版本鎖死：雛型 v3 → Figma v3 → 規格 v3，圖永遠同版
  • 先定「誰是視覺單一來源」→ 規格就從它抽圖
所以議題三的決策核心＝先定哪一個是視覺單一來源（下一頁 A/B/C）；規格的圖一律從那一個自動產生，才能保證「規格圖＝Figma＝HTML」不分岔。

議題三（2/4）AI 產圖：兩種情境、兩套做法

情境不同、做法不同。這是 PM 現場最需要對齊的操作細節。

延續案：像「同一套系統的下一頁」
  1. PM 收齊既有系統截圖當素材
  2. AI 跑 design-baseline 抽視覺基準（配色/字體/間距/圓角陰影/元件）
  3. 產唯一一份 _shared.css ＋ 設計基準.md
  4. 雛型錨定 css，過「反 AI 感」檢查清單

分工：PM 給素材＋定案 · AI 抽色票＋產雛型 · 設計視需要微調（常可跳過 Figma）

新案：需要新穎風格
  1. AI 產 2–3 種風格方向（低精度草稿）
  2. PM＋設計選一個定調
  3. 定調後回寫唯一一份 _shared.css，之後只追加不重寫
  4. 才進入功能雛型量產

分工：AI 產風格草稿 · 設計 定調把關 · 之後 AI 依定案產各畫面

新案的視覺探索是 AI 最不穩、最需要人把關之處——別讓它一次到底，務必留「人選定調」這一關。

議題三（3/4）Figma：三選一，明確選一個

HTML ⇄ Figma 雙向同步 = 兩份會各自演化的來源，正是鐵律一號要防的事。核心原則：同一件事不要兩邊都能改。
選項（視覺真實來源）工作流（具體）優點代價適用
A. HTML 為主
SoT ＝ PMflow HTML		 AI 產 HTML 雛型 →（需精修時）單向匯進 Figma 給設計潤 → 潤後當交付參考，不回寫 單一來源、最省轉手 設計要在 HTML/CSS 上調，或精修版不回流程 延續案、想極簡
B. 關注點分家
視覺＝Figma／行為＝HTML		 HTML 只管互動＋SPEC；Figma 只出最終視覺；PG 視覺看 Figma、規則看規格 各用所長、新案視覺自由 要嚴格劃清「視覺 vs 行為」，兩邊要對得上 新案、重視覺
C. 維持現狀
SoT ＝ HTML		 不進 Figma，把 AI 產圖品質拉高到可直接交付 PG 流程最單純、零回流風險 新案視覺探索能力受限 延續案
關鍵保證：不論 A/B/C，規格圖一律「自動從選定的視覺來源產生」、不手動另存，才能保證「規格圖＝Figma＝HTML」。先定來源，再談工具。

議題三（4/4）怎麼選、會前先答什麼、怎麼試

判斷準則（建議預設）

  • 延續案 → 預設 A 或 C（視覺已被既有系統框住，Figma 邊際效益低）
  • 新案且視覺是賣點 → 傾向 B
  • git／工具紀律還沒建立 → 先 C，最單純

工具現實（要誠實面對）

  • HTML→Figma（html.to.design 等）：圖層會亂、元件會散
  • Figma→HTML（Anima／Dev Mode）：產的 code 不合 _shared.css 規範、不帶 SPEC
  • → 這就是「回流不可靠」的根本原因

會前先答三題

  • 這案子視覺是不是賣點／差異化？
  • 設計師願在 HTML/CSS 上調，還是非 Figma 不可？
  • 潤稿後的視覺要不要回到 PMflow，還是只當交付？
試辦建議：挑一個延續案試 A／C、一個新案試 B，各跑一輪，量「設計重畫工時」有沒有下降，再回頭定案全公司標準。

議題四（1/2）四個存放方案評估

先分兩個需求：①存取（大家打得開）雲端/NAS 就能解；②收斂（多人不分岔、可追溯）才是分道揚鑣的關鍵。

只有 Git 能解②「防分岔＋可追溯」；雲端/NAS 在①存取與重檔上更省事、PM 也更好上手。→ 不是四選一，看下一頁的組合。

議題四（2/2）評估結論與導入建議

關鍵能力（防分岔＋可追溯）只有 git 有，但學習曲線與重檔要配套——所以是「組合」，不是四選一。

建議組合（各取所長）

  • Git = 唯一真版（文字產物：雛型/規格/確認紀錄/memory）
  • 雲端／NAS = 重檔倉庫、備份、給非技術者的分享連結
  • 特定主機（選配）= 雛型發佈站，PL/PG 開網址看最新
  • 分工：主PM 專案層跑一次／功能PM 各自功能夾平行

要一起討論的做法

  • 現在就上 git（PM 用 GitHub Desktop 等 GUI，不碰指令）？
  • 還是先雲端過渡：單一雲端 ＋「共用檔負責人制」（每個共用檔一個 owner，別人改先講）？
  • 過渡法能止血，但擋不住根本分岔——何時轉 git？
重點提醒：不論最後放哪，git repo 不要放進會即時同步的雲端資料夾（內部檔案會被同步弄壞）。

議題五：資料夾架構（支援專案管理）

把「主PM 層 vs 功能層」「輸入 vs 產物」在資料夾上切成看得見的界線。

專案/{專案名}/ ├── 00_專案管理/ 【主PM】專案總覽 · 時程里程碑 · 決策紀錄 · 風險待辦 · 角色聯絡 ├── 10_專案素材/ 【主PM 跑一次】原始「輸入」：合約 · 會議簡報 · 會議原始記錄 · 轉檔MD ├── 20_專案文件/ 【AI 產·主PM 覆核】「衍生」：會議紀錄 · 服務建議書 · 報告書 · 技術文件⚠ ├── memory/ 【主PM 跑一次】專案 AI 記憶（功能PM 只讀） ├── _設計系統/ 【主PM 跑一次】唯一一份 _shared.css ＋ 設計基準（全功能共用） ├── _封存/ 只讀墳場 └── 功能/ 【各功能PM 各自擁有 · 平行不撞】 └── {功能名}/ 01_需求整理 · 02_雛型 · 03_規格 · 04_設計稿 · 05_驗收 · 06_變更
重點三招：新增 00 專案管理層、10 輸入與 20 產物嚴格分家（自動產文件的前提）、_shared.css 升到專案級只抽一次色票（省 token）。
會議紀錄兩版本：PMflow 讀「速筆（會議原始記錄）」轉 MD 當輸入；「給客戶正式版」是 20_ 的產物（現階段先不做），不可回頭當輸入（避免有損迴圈）。

界線澄清：素材 vs 確認紀錄

功能PM 訪談完跟 AI 講的確認事項，不進 10_專案素材——它是功能層的決定。

素材確認事項
本質外面進來的原始證據（合約、簡報、逐字稿）對話中產生的決定（客戶拍板、PL 意見、PM 決定）
誰寫主PM，跑一次功能PM，持續累積
去哪10_專案素材/（唯讀為主）寫回雛型 ＋ 該功能 確認紀錄/
若讓確認事項流進素材，會同時破壞三件事：①「跑一次」失效（多人持續寫）②單一來源被複製 ③商業稽核線弄髒。
一句話：「外面進來的、跨功能的」歸主PM 的 10_ 跑一次；「討論產生的、單功能的」歸功能PM 的雛型＋確認紀錄持續寫。兩條水管永不交叉。

角色分工：把 PL 往前拉是投報最高的一招

最核心的組織痛是「技術團隊太晚進場」。分工圍繞這件事重排。

角色現在建議調整
業務投標畫粗雛型（另一份）改用 PMflow 投標視圖產願景雛型；標「示意 vs 承諾」；合約範圍初判
PM得標後接手，主線到規格主線不變，多一責任：雛型 v1 完成後、客戶訪談前先找 PL 過可行性；PM 不做技術判斷
PL需求說明才進場提前到雛型 v1：對 ⚠️待技術確認 圖層做檢核，翻案風險在最便宜的階段攔下（設為強制關卡）
PG需求說明才拿到完整細節讀「AI 讀版」開發、開「驗收清單版」自測；任務拆解/API/DDL 仍屬技術團隊
設計整體重畫 XD/Figma延續案：直接精修 HTML/CSS；新案：只做視覺探索與定調，不從零重畫
一句話：把 PL 的介入點從「需求說明」拉到「雛型 v1」，翻案成本從最貴階段移到最便宜階段。

議題六（1/2）流程時間點：文件何時給 PL 看

TIMING > DOCUMENT

產了文件，沒在對的時間點給 PL＝沒用

錨點原則：每個「對外動作」之前，先過 PL 技術關——給客戶之前、交付 PG 之前。

時機給 PL 什麼PL 要回答若卡住怎麼辦
① 雛型 v1 完成、寄訪談簡報給客戶「之前」雛型連結（?spec）＋ ⚠️待技術確認清單這些畫面/流程做得出來嗎？哪些要調？不可行的先別放進給客戶的簡報
② 客戶訪談「之後」、回填升版後更新後雛型 ＋ 本次確認/變更摘要客戶新加的有沒有新風險？有風險先標記，下次對外前再確認
③ 規格定稿、正式交付 PG「之前」規格（AI 讀版）＋ 驗收清單照這規格開發可行嗎？範圍有沒有爆？有疑慮回雛型改，再同步規格
時機對了，文件才有用。這三個關卡都錨在「對外動作」前，正好對應議題四的 PR/MR 檢核與發佈站連結。

議題六（2/2）PL 跨專案、還沒投入的專案怎麼辦？

整包丟給 PL「有空看」＝沒有時限、會太晚、看不完。核心：分級 ＋ 非同步 ＋ 只丟聚焦問題。

先分級，不要整包丟
  • 🟢 可自決跟舊系統一致／業界慣例／我方可決定 → PM 直接拍板，不佔 PL 時間
  • 🟡 技術疑慮 → 只丟這幾條給 PL，不是整份文件
  • 🔴 高風險/可能翻案 → 必須 PL 同步討論
  • 給 PL 的是「聚焦問題 ＋ 雛型連結」：開發佈站看畫面、只答被標記的幾題
非同步 ＋ 尚未投入的專案
  • 附需回覆日（錨定「客戶訪談日前 X 天」）；設每週技術 triage 時段一次過
  • 還沒派 PL 的專案：指定「技術窗口／值班 PL」做輕量掃描（只擋明顯不可行）
  • 真的排不進：PM 把假設標 ⚠️技術假設(未經PL確認)，照常規劃但不對客戶承諾
  • 這些假設列為啟動會議強制複審清單
核心原則：未經 PL 確認的技術假設，可以繼續規劃，但不可對外承諾、且必留顯眼待複審標記。既不卡 PM 進度，又不讓風險溜過。

議題七（1/2）接上開發現實：讀既有 DB / API

現在流程沒讀開發會用的資料（DB、API），PM 憑需求定義欄位，容易跟既有系統對不上，PG 開發時才發現。

建議做法

  1. 把既有系統的 DB schema（DDL/ERD） 與 API 文件（Swagger/清單） 放進 10_專案素材/既有系統資料/
  2. material-intake 讀進 memory，讓雛型/規格能引用真實欄位與 API
  3. 雛型 SPEC 的「資料來源」標實際 table.column／API endpoint
  4. 規格欄位表加一欄「對應資料來源」

邊界（維持 PM 主線界線）

  • 這是「讀既有的當參照」讓需求落地
  • 不是 PM 設計新 DDL／新 API——新表/新 API 仍屬技術團隊
  • 主要利延續案（全新案還沒有 DB/API 可讀）
  • 誰提供：PL/PG 或主PM 收進 10_，跑一次共讀
效益：雛型欄位與既有系統從第一版就對得上，減少 PG「這欄位/這 API 不存在」的翻案。呼應鐵律一號——讓雛型 SPEC 更貼近現實。
