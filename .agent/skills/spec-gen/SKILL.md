# /spec-gen — 規格定稿

把定稿的 HTML 雛型（帶 SPEC 註解）轉成**結構化需求規格**，作為 PG 開發與驗收的**唯一標準**。

這是整條流程省時最大的環節：把「PM 手寫規格」變成「PM 審閱 AI 草稿」。規格不是從零寫的 —— 原料就是雛型裡的 SPEC 註解、📋 規格區塊與歷次確認紀錄。

**規格就是驗收標準。** 本流程不再另外產一份驗收清單 —— 規格的 §六 AC 表自帶 PG 自測與 PM 驗收的勾選欄，兩邊照同一份走，驗收標準不會各自解讀。

## Usage

```
/spec-gen 專案/{專案名}/功能/{功能名}/02_雛型      # 首次產出，或雛型改版後同步
/spec-gen 專案/{專案名}/功能/{功能名}              # 同上，AI 自己找雛型
/spec-gen <...> --只出 設計交付                    # 只重產設計端交付說明
```

路徑慣例：

- 輸入：`功能/{功能名}/02_雛型/` —— **取檔名版本號最大的 `雛型_v{n}_*.html`**（舊版保留是為了對照，不是規格來源）
- 同時讀：`01_需求整理/01_需求摘要.md`（含「六、待定與需確認事項」的結論欄）、`01_需求整理/確認紀錄/`（歷次確認的答案在這）、專案 `memory/`（技術棧、介接方式、系統現況）
- 產出：`03_規格文件/01_需求規格_{功能名}_v{n}.md` ＋ `03_規格文件/畫面截圖/` ＋ `04_設計稿/00_設計交付.html`

前置：需求與雛型已經穩定（`/req-intake` 跑到沒有新的未決項）。若還有大量 Q- 編號沒結論，提醒 PM 但仍可先產草稿，待定處標清楚。

## 步驟 1：判斷首次產出或更新模式

`03_規格文件/` 已有規格 → **更新模式**，不是重做：

- 逐項比對「最新雛型 ↔ 既有規格」，只改異動處並標 `【更新 {日期}】`
- **保留 PM 手動補充的內容**（他補的業務背景、跟客戶談出來的細節、主管的技術裁示都在裡面，重生一次就洗掉了）
- 規格版本號跟雛型走：雛型升到 v3 → 規格改名／改標題為 v3
- 若 `06_變更紀錄/` 有比規格版本新、尚未反映進規格的變更，先列出來提醒 PM
- 更新完在文件開頭的「版本紀錄」加一列：改了什麼、依據哪一版雛型

## 步驟 2：讀取與盤點

1. 讀最新版雛型每一支 HTML，抽取：
   - `<!-- SPEC: ... -->` 註解（含 F-編號與【明確】【新增】等來源標記）
   - `?spec=1` 才可見的「📋 本畫面規格」區塊：欄位表、業務規則、例外流程
   - `【調整 v{n}】` 異動標記 —— 這些是確認迭代的結果，規格必須反映最新狀態
   - 討論模式面板裡**還沒定案**的項目 → 這些是待定清單的來源
2. 讀 `01_需求摘要.md`（背景、目標、F-需求、範圍界定、Q- 編號結論）與 `確認紀錄/`（客戶與主管實際答了什麼）。
3. 讀專案 `memory/`：技術棧、既有系統的介接方式與資料表現況 —— 規格裡的技術性描述要以這些為依據，**不要臆造**。

## 步驟 3：缺口盤點（先問再寫）

收集所有 `TODO：待確認`、沒結論的 Q- 編號、雛型與需求摘要矛盾處，**在對話中一次問齊 PM**（不要一題一題來回）。PM 答不出來的標 `【待定】` 集中列進附錄，**不要編造成既定事實**。

若缺口多到規格會有一半待定 → 建議 PM 先回去跑 `/req-intake` 收斂，不要硬產。

## 步驟 4：生成規格

依下方範本產出 `03_規格文件/01_需求規格_{功能名}_v{n}.md`。品質要求：

- **欄位表以雛型 SPEC 為準**；與需求摘要衝突時先問 PM，不要自行擇一。
- **需求摘要不會寫欄位細節**（那是刻意的分工），所以欄位表的唯一來源就是雛型 —— 雛型 SPEC 缺的就是規格缺的，缺了要回頭補雛型，不要在規格裡自己補一套。
- **業務規則與邊界條件**是 PG 最需要、最容易缺的：數值上下限、空值行為、權限差異、日期區間規則都要明寫。
- **例外流程要寫出實際錯誤訊息文案**（客戶會看到的字），不是「顯示錯誤訊息」。
- **追溯表**把 F-編號 ↔ 畫面 ↔ 規格章節 ↔ AC 串起來。之後變更要算影響、驗收要對帳都靠它。

## 步驟 5：驗收條件（AC）—— 這一節就是驗收清單

**AC 不只抄主流程。** 本流程沒有獨立的驗收清單文件，所以 AC 必須自己涵蓋完整測項，缺一類就會漏驗：

| 類別 | 展開方式 |
|---|---|
| **主流程** | 每條 User Story／F-需求至少一條 AC（Given / When / Then） |
| **欄位驗證（負向）** | 從欄位表的驗證規則逐欄展開：必填留空、超出長度／範圍、格式錯誤、特殊字元、重複值 |
| **例外流程** | 規格例外表每一列一條 AC，**Then 要含實際錯誤訊息文案** |
| **權限與資料範圍** | 每種角色各一組：能做什麼、不能做什麼、看到的資料範圍 |
| **非功能** | 規格有寫才出：大資料量匯出、逾時行為、無障礙要求等 |

寫法規則：

- **Given / When / Then 必須可測**：有具體輸入值與可觀察的預期輸出。禁止「應正常運作」「畫面顯示正確」這種寫法。
- **具體到非開發者照著做就能完成**：輸入什麼值、點哪個按鈕、應該看到什麼畫面或訊息。
- 每條 AC 標 `對應 F` 與類別（主流程／驗證／例外／權限）。
- 表格自帶 **`PG自測` 與 `PM驗收` 兩個 ☐ 欄** —— PG 交付前逐項自測勾左欄，PM 驗收勾右欄，同一份文件兩種用途。

`05_驗收/` 只放**驗收結果**（勾選後的副本、不通過項目的處理紀錄），不再產另一份清單。

## 步驟 6：一致性檢查

三方比對「需求摘要 ↔ 雛型 ↔ 規格」，列出：

- 需求摘要有、但雛型沒畫到的 F-編號
- 雛型有、但需求摘要沒有且未標 `【新增】` 的元素
- 欄位表與畫面實際元素不符處（名稱、必填、選項值）
- 有 F-編號但沒有任何 AC 覆蓋的需求（**最容易漏，也最容易在驗收翻車**）

結果寫進規格附錄，並在對話中回報 PM 逐項確認。

## 步驟 7：畫面截圖

用 headless 瀏覽器對每個畫面截圖（**乾淨模式，不要帶討論圖層**），存 `03_規格文件/畫面截圖/`，檔名帶版本與畫面名。規格的畫面章節引用這些圖，讓 PG 不用另開雛型也能看懂。

```bash
chrome --headless --disable-gpu --screenshot=out.png --window-size=1500,1200 --hide-scrollbars "<HTML 的完整絕對路徑>"
```

必須給**完整絕對路徑**，否則 Chrome 會當成網址去查 DNS，截出「無法連上這個網站」。非理想狀態（空清單、錯誤、無權限）也各截一張 —— 設計與 PG 都需要。

要截帶查詢字串的畫面（如 `?spec=1`）必須改用 `file:///` URL 形式、中文路徑 URL-encode，否則 Chrome 會把整串當檔名截出「無法存取你的檔案」。用 Python 產：`"file:///" + urllib.parse.quote(Path(f).resolve().as_posix()) + "?spec=1"`。

## 步驟 8：設計端交付（PM 派工用）

產 `04_設計稿/00_設計交付.html` —— **單頁、自包含、離線可開**，設計端不必啃整份規格，也不必在多個資料夾之間跳。

實作要求：

- **引用到的圖片一律複製進 `04_設計稿/圖/`**，用相對路徑引用。設計拿到 `04_設計稿/` 一個資料夾就能work，不要叫他去 `02_雛型/` 或 `03_規格文件/` 找圖。
- 版面：左邊畫面截圖、右邊「這張要改什麼」，一個畫面一段。
- 樣式內嵌或複製一份 css 進同夾，不依賴外部 CDN。

內容**只放設計真正需要決定的三件事**，其餘不要放：

1. **要出什麼** — 畫面清單（含截圖）＋ 待設計交付的素材（icon、圖檔、色票）
2. **不可以動什麼** — 欄位、互動、文案不可自行增減；少一個欄位或多一個按鈕就會讓規格、開發與驗收對不上
3. **非理想狀態也要出圖** — 空清單、查無資料、欄位錯誤、無權限，逐項列出畫面表現

若設計稿已存在且與規格有出入，加一節逐項對照（設計稿怎麼畫／規格怎麼定／以誰為準），原則：**UI（配色、版面、樣式）可採設計稿，UX 與規格一律以需求規格為準。**

**不要放**：規格章節速查表、業務規則全文、AC 清單、資料表與 API 說明。設計不會看，放了只會讓他找不到重點。

## 步驟 9：收尾引導

- 規格草稿已產出，請 PM **審閱業務細節**，特別是附錄的 `【待定】` 清單
- 標 `【待技術確認】` 的請技術主管確認後，跑一次 `/req-intake` 回填雛型再重跑本 skill（**不要直接改規格**）
- 一致性檢查發現的落差逐項回報，請 PM 決定怎麼處理
- 設計交付頁在 `04_設計稿/00_設計交付.html`，可直接寄給設計或投影
- 定稿後：這份規格就是**交付技術團隊的唯一依據**，AC 表同時是 PG 自測與 PM 驗收的清單
- 之後任何需求變更**不要直接改規格** —— 一律回 `/req-intake`，從雛型改起，AI 會列出規格哪幾章要跟著改


## 注意事項

- **PM 沒有技術背景**：對話中的說明用白話；規格文件本身可用精確術語（讀者是 PG）。
- **規格是抽取出來的，不是手寫的。** 雛型 SPEC 沒寫的東西，回頭補雛型，不要在規格裡自己發明 —— 那會讓雛型不再是單一真實來源。
- **不確定的一律標 `【待定】` 或 `【需 PG 確認】`**，不要為了完整而編造。與既有系統資料表、既有 API 有關的描述尤其要標。
- **規格版本號永遠跟雛型一致**；改版一律從雛型發動。
- **AC 就是驗收清單**，所以寧可多展開負向與權限測項，不要只寫得漂亮。
- Markdown 表格可直接貼進 Google Doc；團隊要求 gdoc 交付時提示 PM 複製貼上即可。
- 上游是 [req-intake]。定稿後交付技術團隊（開發任務拆解、API、資料表由技術團隊自行處理，不在 PM 主線）。
