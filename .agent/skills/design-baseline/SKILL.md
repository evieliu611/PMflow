# /design-baseline — 視覺基準建立（proto-gen 前置）

解決「雛型畫面一眼看穿是 AI 生成」的問題。AI 感的根因是**沒有視覺錨點**：模型沒有參照物時，就退回它的預設審美——紫藍漸層、emoji 當功能 icon、過度圓角與陰影、置中大卡片、Lorem ipsum 假資料、間距亂無節奏。這支 skill 給雛型一個真實錨點：**從客戶既有系統截圖抽出視覺基因**，寫成雛型可直接套用的 CSS 變數與元件樣式，讓畫面看起來像「這套系統本來就長這樣」。

放在 [proto-gen] 之前跑一次（每個專案一次，之後功能共用）。

## Usage

```
/design-baseline 專案/{專案名}                          # 從該專案 _共用素材/現有系統截圖/ 抽基準
/design-baseline 專案/{專案名} --參考 <某張截圖路徑>      # 指定最具代表性的畫面當主基準
/design-baseline 專案/{專案名} --新專案                   # 無舊系統或要重設計：抽基因後合理延伸（見下）
```

路徑慣例：
- 輸入：`專案/{專案名}/_共用素材/現有系統截圖/`（或 req-intake 挑進各功能 `01_需求整理/參考截圖/` 的圖）
- 產出：`專案/{專案名}/_共用素材/設計基準.md` ＋ `專案/{專案名}/_共用素材/_shared.css`
- 之後每個功能的 `02_雛型/` 直接複製或 `@import` 這份 `_shared.css`，多功能自動長得像同一套系統

## 兩種情境（對應 PM 實務）

- **舊專案 / 已有既有系統**（如農水署）：雛型**必須對齊**舊系統。抽出的基準就是硬約束，不自由發揮——目標是新畫面像「同一套系統長出來的下一頁」。
- **新專案 / 會重設計版面**：舊系統截圖是**基因來源不是照抄稿**。抽出配色與元件風格當地基，版面/欄位可重新設計，但不引入與基因衝突的新審美（例如舊系統務實樸素，就別加漸層與大圓角）。`--新專案` 模式下，抽完基準要在對話中跟 PM 確認「哪些沿用、哪些重設計」。

## What You Must Do When Invoked

### 步驟 1：找到並視覺讀取截圖
1. 掃 `_共用素材/現有系統截圖/`（沒有就問 PM：有沒有客戶舊系統的畫面？連 email 裡的截圖、合約附的示意圖都算）。
2. **用 Read 工具視覺讀取**每張截圖（不是看檔名猜）。優先讀：列表/表格頁、表單頁、含側欄的主框架頁——這三類最能定義一套系統的視覺語言。
3. 完全沒有任何舊系統畫面 → 這支 skill 幫不上「對齊」，改走「通用去 AI 感」：直接套用下方**反 AI 感檢查清單**與一組中性務實的預設基準（參考農水署 `_shared.css` 的取值範圍），並明講「這是通用基準，不是對齊某系統」。

### 步驟 2：抽出視覺基準（八個維度，看圖填值）
逐張截圖觀察，歸納成可量化的值。判不準的標「約」或列兩個候選給 PM 選，不要硬編：

| 維度 | 要抽什麼 | 對應 CSS |
|------|----------|----------|
| 主色系 | 主色（按鈕/連結/選中態）、深色變體、輔色 | `--brand` `--brand-d` |
| 中性色 | 文字色、次要文字、分隔線、頁背景、卡片白 | `--ink` `--muted` `--line` `--bg` `--white` |
| 語意色 | 成功/警告/危險/資訊 | `--ok` `--warn` `--danger` |
| 字體 | 字族（中文系統常見正黑體）、基準字級、標題字級階層 | `body` `h1` |
| 圓角 | 卡片/按鈕/輸入框的圓角程度（舊後臺多半 4~8px，不要動輒 16px+） | `border-radius` |
| 陰影 | 有無、多重？（務實後臺通常極克制，靠邊框分層而非陰影） | `box-shadow` |
| 間距節奏 | padding/gap 的基本單位（常見 4 的倍數）、卡片內距、欄間距 | `padding` `gap` |
| 元件樣式 | 側欄寬與選中態、表格表頭底色/框線、表單 label 位置、按鈕主次樣式、徽章/tag 樣式 | 各 component class |

### 步驟 3：產出 設計基準.md
**`_共用素材/設計基準.md`**：

```markdown
# {專案名} 視覺基準
> 建立日期：{今日}｜基準來源：{列出讀了哪幾張截圖}｜情境：對齊舊系統 / 新專案延伸 / 通用

## 一、色票
| 用途 | 變數 | 色值 | 說明 |
|------|------|------|------|
| 主色 | --brand | #1f7a8c | 按鈕、連結、選中態（取自舊系統標題列） |
| ... |

## 二、字體與字級
- 字族：{}｜基準字級：{}px｜H1：{}px｜標籤：{}px

## 三、形狀語言
- 圓角：{}px（卡片）/ {}px（按鈕輸入框）
- 陰影：{克制/無/具體值}——分層主要靠 1px 邊框
- 間距單位：{}px 的倍數

## 四、元件風格（雛型要沿用的）
- 側欄：寬 {}px、選中態 {}、群組標題 {}
- 表格：表頭底色 {}、列高、hover {}、框線 {}
- 表單：label 在欄位上方/左側、輸入框樣式、必填標示
- 按鈕：主要 {} / 次要 {}
- 徽章 tag：{}

## 五、本專案的「反 AI 感」重點（依舊系統特徵）
（例：舊系統無漸層無陰影、圖示用文字不用 emoji、資料密度高——雛型都要跟）
```

### 步驟 4：產出 / 更新 _shared.css
**`_共用素材/_shared.css`**——把基準落成 CSS 變數（`:root`）與元件 class，讓雛型直接套。
- 已存在（同專案第二次跑）→ **更新模式**：只調整抽到的變數值，保留既有 class 結構與 PM/前次的手動微調，不整份重寫。
- 結構參照農水署那份的骨架：`:root` 變數 → body/連結 → 框架(app/aside/main) → 卡片/表單/表格/按鈕/tab/彈窗/徽章。**規格折疊區（.spec）樣式必須保留**，那是 proto-gen 內嵌半成品規格用的，不屬於客戶視覺但雛型需要。

### 步驟 5：反 AI 感檢查清單（寫進基準、proto-gen 強制遵守）
把這份清單寫進 `設計基準.md`，並在收尾提醒 proto-gen 產圖時逐條對照：

- ❌ **禁紫藍漸層/彩色漸層背景**——AI 味最重的來源；用純色或極淺的單色底。
- ❌ **禁 emoji 當功能 icon**（🚀📊✨ 這類）——後臺系統用文字標籤或線性 icon；狀態徽章用色塊+文字。
- ❌ **禁 Lorem ipsum / 「範例文字」**——用**貼近本專案的真實假資料**（真的案場名、真的日期格式、真的金額量級，取自需求摘要/截圖）。
- ❌ **禁過度圓角**（>12px 的大圓角、藥丸按鈕滿天飛）——對齊舊系統的克制圓角。
- ❌ **禁浮誇陰影/毛玻璃/霓虹光暈**——務實後臺靠邊框與底色分層。
- ❌ **禁置中巨型卡片 + 大量留白的 landing page 風**——後臺是資訊密度高的工作介面，左側欄+主內容區。
- ✅ **對齊資料密度**：舊系統一頁塞多少資訊，雛型就給相近密度，不要為了「好看」放大留白。
- ✅ **字體用系統中文字體**（正黑體/思源），不要為了設計感套花俏 web font。
- ✅ **色彩克制**：主色 + 中性灰階 + 少量語意色即可，不要每個區塊一個顏色。

### 步驟 6：收尾引導
- 對 PM 回報：抽了哪幾張截圖、定出的主色與風格重點、產出 `設計基準.md` 與 `_shared.css` 在哪。
- `--新專案` 模式：列出「建議沿用 vs 可重設計」讓 PM 拍板。
- 下一步：`/proto-gen 專案/{專案名}/功能/{功能名}/01_需求整理`——proto-gen 會自動繼承這份 `_shared.css` 與檢查清單。

## 注意事項
- **唯一真實來源仍是雛型 HTML**：這支只管視覺基準，不碰欄位定義/互動行為（那是 proto-gen 的 SPEC 註解）。基準是「怎麼看」，SPEC 是「是什麼」。
- **不臆造舊系統的色值**：截圖模糊、判不準的顏色，列候選給 PM 選或標「約」，不要編一個精確 hex 當事實。
- **一個專案一份基準**：多功能共用同一份 `_shared.css`，這正是「多功能看起來像同一套系統」的來源。功能間若需差異（不同模組不同色），在基準裡開分支變數，不要各功能各自一套。
- 這是 [proto-gen] 的前置；變更視覺風格（客戶說「顏色改一下」）走 [change-impact] 從基準改起再往雛型推。
