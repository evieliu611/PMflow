# 華南 PMflow — AI 協作開發工作區

PM 透過 AI 協作的需求開發工作區。從零散需求到雛型、規格定稿，串成一條單一真實來源的流程，再交付技術團隊開發。

## 目錄結構

```
PMflow/
├── README.md                  ← 本檔
├── AI協作開發流程規劃.md        ← 完整流程說明（為什麼這樣設計）
├── 新PM上手說明書.md            ← 新 PM 必讀：逐步操作手冊
├── .claude/
│   ├── skills/                ← PM 主線三支 skill
│   │   ├── material-intake/   ← /material-intake  素材整理
│   │   ├── req-intake/        ← /req-intake       需求整理與確認（主力）
│   │   └── spec-gen/          ← /spec-gen         規格定稿
│   └── _停用skills/           ← 2026-08-03 簡化後停用的五支（不會被載入，說明見該夾 README）
└── 專案/
    ├── _範本專案/              ← 複製改名即可開新專案
    ├── 新北景觀/               ← 進行中的真實案例
    └── 農水署/                 ← 進行中的真實案例
```

## 流程

```
素材整理  →  需求整理／需求確認  →  規格定稿  →  交付技術團隊
             ↺ 雛型與客戶／主管反覆確認（跑幾次都行）
```

| Skill | 什麼時候跑 | 做什麼 |
|-------|-----------|--------|
| `/material-intake` | 拿到新素材 | 讀懂每份檔案、分類歸檔到 `_共用素材/`、重點寫進專案 `memory/` |
| `/req-intake` | ①初次整理 ②訪談／主管討論後回填 ③規格產出後要改 | 逐輪選擇題收斂需求 → 產需求摘要＋可點擊 HTML 雛型；回饋逐條歸戶回填並升版；新需求先判合約範圍 |
| `/spec-gen` | 需求穩定要定稿；雛型改版後同步 | 從雛型 SPEC 註解抽出正式規格（欄位表／業務規則／可勾選 AC）＋一致性檢查＋設計端交付頁 |

**`/req-intake` 是主力，一個功能會跑很多次。** 模式由 AI 依資料夾現況判斷，你不必記參數。要出去見客戶時加 `--訪談準備`，它會先把「你自己就能決定」的題目當場問掉，只把需要客戶拍板的寫進訪談清單。

## 開新專案

```bash
# 複製範本，改成實際專案名
cp -r 專案/_範本專案 專案/訂單管理系統
```

然後照 `專案/{專案名}/README.md` 的動線走。詳細操作見 [新PM上手說明書.md](新PM上手說明書.md)。

## 三條鐵律

1. **單一真實來源 = HTML 雛型**：欄位定義、驗證規則、互動行為以 SPEC 註解內嵌在雛型裡，規格是從雛型抽取的。
2. **一切變更從雛型改起**：不要直接改規格或 AC，先改雛型再讓 AI 算下游影響。
3. **需求摘要要薄、雛型 SPEC 要厚**：同一件事只寫一處，寫兩處必然對不上。

## 2026-08-03 流程簡化

原本八支 skill、六階段（0／1／1.5／2／3／4）已收斂成三支。停用的 `proto-gen`、`feedback-merge`、`change-impact`、`accept-gen`、`dev-kit` 移到 `.claude/_停用skills/`，能力併入去向見 [該夾 README](.claude/_停用skills/README.md)。

主要變化：

- **雛型升級與訪談準備**併入 `/req-intake`（不再有 v0／v1 的區分，雛型從 v1 起算）
- **訪談回饋回填**與**需求變更**都是 `/req-intake`（同一個指令，AI 判斷模式）
- **驗收清單**併入規格的 §六 AC（自帶負向與權限測項、`PG自測`／`PM驗收` 勾選欄）—— 規格就是驗收標準
- **設計交付**併入 `/spec-gen`，產單頁自包含的 `04_設計稿/00_設計交付.html`
- **開發任務拆解／API／DDL** 不再由 PM 主線產出，屬技術團隊
